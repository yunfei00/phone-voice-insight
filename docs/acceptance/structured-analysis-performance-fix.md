# AI 结构化分析页面超时与聚合性能修复报告

## 1. 修复前审查

审查基线：`origin/main@5c08ca3`。

### 已经具备，无需重复实现

- 结构化分析结果、质量、聚合、批次和语料进度 API 已存在。
- Celery 批次已具备 `PENDING`、`RUNNING`、`SUCCESS`、`PARTIAL`、`FAILED`、`CANCELLED`、`PAUSED`、`BUDGET_EXCEEDED` 状态。
- 数据库已有 `ReviewRecord(product, published_at)`、`ReviewRecord(source, record_type, published_at)`、`OpinionAspect(analysis_id)` 和分类组合索引。
- Nginx SSE 路径已有 300 秒读取超时；普通 JSON 聚合请求不会在前端 60 秒前被代理主动终止。

### 未修复问题

1. 前端四个主请求使用单个 `Promise.all`，任何接口失败都会阻断全部模块并清空本轮更新。
2. 页面每 5 秒执行一次完整 `load()`，重复请求结果、质量、聚合、批次、分类和进度。
3. `aggregates` 沿用全局 10 秒 Axios 超时，没有单接口超时策略。
4. 全局 Axios 拦截器对轮询失败持续弹出消息，组件缺少模块级错误隔离。
5. 产品快速切换没有请求代次和取消控制，旧响应可能覆盖新产品数据。
6. 定时刷新没有进行中请求保护，慢请求可能重叠。
7. 页面直接展示英文批次状态，前端类型缺少后端已有的 `PAUSED`、`BUDGET_EXCEEDED`。
8. 后端 `_anomalies()` 对每个主题执行最近 7 天与此前 28 天两次 COUNT，形成 `1 + 2N` 查询。
9. `content_count` 与 `opinion_count` 分别查询，存在可合并的重复聚合。

### 需要验证

- PostgreSQL 下 1,000、10,000、50,000 条观点的响应时间、SQL 数量和执行计划。
- 是否需要新增复合索引；只有执行计划证明有效时才新增迁移。
- Docker 构建、迁移检查、反向代理和生产数据规模下的接口响应。
